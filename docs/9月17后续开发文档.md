完成从用户语音输入到有依据语音回答的完整链路：

```text
麦克风采集
```

### 4.1 P0：数据库与环境就绪

1. 在测试数据库上执行：
   - `t_knowledge_document.sql`
   - `t_user_realtime_chat_history.sql`
   - `t_user_role_assignment.sql`
2. 确认旧数据保留完整，新表可正常读写。
3. 配置启动管理员，验证普通用户与管理员权限区分。
4. 整理本地启动参数，密钥仅保存在本地环境文件中，禁止提交至 Git。

必需配置项包括：

```text
APP_BOOTSTRAP_ADMIN_USERNAME
RAG_SERVICE_URL
REALTIME_GATEWAY_INTERNAL_KEY
DEEPSEEK_API_KEY
DEEPSEEK_MODEL
XFYUN_TTS_APP_ID
XFYUN_TTS_API_KEY
XFYUN_TTS_API_SECRET
```

完成标准：新数据库和已有数据库均可启动后端，且不依赖手工修改数据才能进入系统。

### 4.2 P0：知识库与 RAG 检索

1. 部署 `services/rag` 服务，配置本地 BGE-M3 模型。
2. 打通文档上传、文本解析、分块、向量化、索引和检索流程。
3. 检索结果必须携带可追溯的文档 ID、片段 ID、文档名称和相关性信息。
4. 当模型缺失、RAG 服务离线、文档解析失败或检索超时时，返回明确错误，不得无限等待。
5. 准备至少 3 份真实演示文档，覆盖正常命中、多文档冲突和无答案三种场景。

完成标准：对同一问题重复测试 10 次，检索服务无崩溃，返回的引用能定位到实际文档片段。

### 4.3 P0：共享知识库权限

当前检索主要依据文档所有者进行隔离。为支持校园公共知识问答，需增加明确的可见范围：

- `PRIVATE`：仅上传者可访问。
- `TEAM`：指定团队或授权成员可访问。
- `PUBLIC`：已发布的普通用户均可检索。

权限判定必须由后端完成，前端隐藏按钮不能代替接口鉴权。检索服务只能接收后端计算出的允许文档集合，不允许前端直接传入任意文档 ID。

完成标准：普通用户可检索公共文档，但无法通过修改请求参数读取他人私有文档。

### 4.4 P0：实时语音问答全链路

1. 前端获取短期连接票据后建立 WebSocket 连接。
2. 音频块按协议发送至实时网关，转写文本按增量事件返回。
3. 语义分段应结合标点、文本长度、等待时间和语义完整度，避免一句话被过早截断。
4. 完整文本进入 RAG 检索，大模型使用检索片段生成回答。
5. 文本回答、引用来源和 TTS 音频并行流式返回。
6. 用户取消当前回合后，必须终止检索、生成与播放，迟到的旧回合事件必须被丢弃。
7. 断网或服务重启后，页面应可恢复到可重连状态，不得长期卡在固定进度。

完成标准：连续进行 20 轮语音问答，无串回合、无重复播放、无无法结束的连接，且每轮历史可正常查看。

### 4.5 P1：管理后台完善

- 支持文档上传、解析状态查看、发布、下线和删除。
- 支持设置用户角色与查看权限结果。
- 展示 Java 后端、实时网关、RAG、ASR 和 TTS 的健康状态。
- 错误界面需要显示可执行信息，例如“RAG 服务未启动”，而不是只显示“请求失败”。
- 禁止在页面、日志或接口返回中显示完整密钥。

### 4.6 P1：测试与故障预案

必须增加以下自动化或可重复的集成测试：

1. 管理员上传并发布公共文档。
2. 普通用户检索已发布的公共文档。
3. 普通用户访问他人私有文档时返回 403 或空检索结果。
4. RAG 服务离线时返回可理解的降级提示。
5. 大模型超时或 TTS 失败时，已生成的文本仍可查看。
6. 用户取消回答后，旧音频不再播放。
7. WebSocket 异常断开后页面可重连。

故障处理原则：语音播放失败不影响文本展示；知识检索失败不得伪造引用；ASR 失败时不得把空文本提交给大模型。

### 4.7 P2：演示与交付资料

- 准备一套固定的演示知识库文档。
- 准备 5 个可稳定命中的问题和 2 个无答案问题。
- 录制或整理一次完整链路的测试结果。
- 在 README 中补充启动顺序、环境变量和常见故障处理方法。
- 准备无外网时的备用演示策略，但必须明确标识备用数据，不能把录制结果宣称为实时调用。

## 5. 建议开发顺序

1. 数据库和环境变量。
2. RAG 模型与单文档检索。
3. 共享知识库权限。
4. 文本输入的 RAG 问答链路。
5. ASR 和语义分段接入。
6. 流式 TTS 与播放取消。
7. 实时历史、管理后台与系统观测。
8. 全链路测试、性能记录和演示资料。

不建议同时调试全部服务。先用文本输入验证 RAG 和大模型，再加入 ASR 和 TTS，更容易定位故障边界。

## 6. 代码与提交要求

1. 每个提交只处理一类明确问题，禁止混入无关格式化或大范围重命名。
2. 不得提交 API 密钥、证书私钥、数据库密码、模型文件和用户真实数据。
3. 涉及数据表变更时，必须同时提交可重复执行的 SQL 或升级说明。
4. 新增功能需要配套测试，修复缺陷需要先补能复现问题的测试。
5. 提交 PR 前先同步最新 `main`，自行解决冲突并重新执行测试。
6. 不直接推送到 `main`，通过 Pull Request 进行合并。

PR 描述必须包含：

- 改动目的。
- 主要文件和接口变化。
- 数据库或环境变量变化。
- 已执行的测试及结果。
- 已知限制与未完成项。
- 演示或验收步骤。

## 8. 阶段验收流程

1. 管理员上传一份校园服务文档并发布为公共资料。
2. 普通用户进入实时语音页面并提出文档相关问题。
3. 页面实时展示转写文字、回答文字、音频播放状态和文档来源。
4. 用户可在回答过程中取消，取消后不再播放旧音频。
5. 问答结束后，可在历史记录中查看问题、回答和引用。
6. 用户尝试访问他人私有文档时，系统拒绝返回内容。
7. 人为停止 RAG 或 TTS 服务，页面给出明确的故障提示并允许用户重试。

以上 7 项全部通过后，本阶段才视为完成。
