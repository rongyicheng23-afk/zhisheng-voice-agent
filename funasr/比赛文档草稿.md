# 特辣油语音工厂项目文档草稿

以下内容依据当前项目代码、目录结构、数据库设计、接口实现和本机实际运行结果整理，可直接作为比赛文档正文初稿使用。文中未对不存在的功能进行扩写；如需补充封面、摘要、团队分工、指导教师等学校信息，可在此基础上继续完善。

## 第一章 需求分析

“特辣油语音工厂”是一个面向语音信息处理场景的综合应用系统，核心目标不是只完成单一的语音识别或语音合成，而是把“录音转文字、实时转写、文字转语音、声纹比对、智能纪要”这些在真实学习和工作中经常连续出现的任务放到同一个平台中统一完成。项目开发的直接背景是：在课堂记录、会议纪要、语音资料整理、角色音色生成和身份核验等场景下，用户往往需要在多个工具之间来回切换，既影响效率，也不利于结果留存和后续追溯。

本项目的目标用户主要包括三类。第一类是学生用户，主要需求是课程录音转写、重点内容整理、会议或小组讨论纪要生成。第二类是教师或管理人员，主要需求是会议记录归档、重点待办提取、发言内容回溯。第三类是对语音处理有进一步需求的内容创作者或实验型用户，他们更关注语音克隆、声纹对比以及统一管理历史语音数据的能力。

从功能需求看，系统需要支持五项核心能力：一是离线录音转文字，要求支持常见音频格式上传，并保存识别历史；二是实时语音识别，要求边录边转、结果持续回显；三是文字转语音，要求上传参考音频并根据输入文本生成目标语音；四是声纹对比，要求上传两段语音后给出相似度与是否同一人的判断；五是智能纪要，要求在转写基础上进一步提取摘要、关键词、待办事项，并支持历史查看和文档导出。

与常见单功能语音工具相比，本项目的特色不在于单项模型指标“绝对最强”，而在于完整链路的工程整合能力。系统前端统一交互，后端统一鉴权与调度，识别与比对结果统一写入数据库，原始音频与结果音频统一存储到 MinIO，对教师和评委而言更容易体现“软件应用与开发”而不是“模型调用演示”。

可将同类方案对比整理为下表：

| 对比维度 | 常见单一录音转写工具 | 常见单一语音合成 Demo | 常见单一声纹工具 | 本项目 |
| --- | --- | --- | --- | --- |
| 功能范围 | 仅转写 | 仅合成 | 仅比对 | 转写、实时识别、合成、声纹、纪要一体化 |
| 账号与权限 | 通常无统一管理 | 通常无统一管理 | 通常无统一管理 | 统一登录、统一历史记录 |
| 数据留存 | 多为临时结果 | 多为临时结果 | 多为临时结果 | 数据库存记录，MinIO 存音频 |
| 结果追溯 | 较弱 | 较弱 | 较弱 | 支持历史查看、回放、导出 |
| 工程完整度 | 单点功能 | 单点功能 | 单点功能 | 前后端分离，多服务协同 |

除功能需求外，系统还需要满足一定的非功能需求：界面交互清晰，普通用户可快速上手；服务模块解耦，便于后续替换模型或扩展功能；历史数据可追溯，便于教学展示和项目答辩；同时保证一定的安全性，通过登录认证控制用户数据隔离。

## 第二章 概要设计

本项目采用“前端展示层 + Java 业务中台 + Python 模型服务 + MySQL + MinIO”的总体架构。前端基于 Vue 3 实现，负责页面展示、用户交互、结果回显和历史管理；Spring Boot 后端作为统一入口，负责登录鉴权、接口编排、业务流程控制、数据库操作和 MinIO 文件管理；Python 服务负责承接具体模型推理；MySQL 用于存储用户信息、历史记录和纪要结构化结果；MinIO 用于保存上传音频、合成结果和切分后的片段音频。

系统总体调用关系可概括为：

`浏览器前端(Vue3) -> Spring Boot后端(8080) -> MySQL + MinIO + Python语音服务`

其中 Python 语音服务又分为三部分：FunASR 文件识别服务运行在 8002 端口，FunASR 实时 WebSocket 服务运行在 10095 端口，XTTS 文字转语音服务运行在 8003 端口，CAM++ 声纹比对服务运行在 8004 端口。前端不直接访问这些模型服务，而是统一通过 Spring Boot 转发调用，这样可以把鉴权、历史记录、文件命名和异常处理集中到一个后端层中完成。

从模块划分看，系统主要包含七个子模块：用户认证模块、录音转文字模块、实时语音识别模块、文字转语音模块、声纹对比模块、智能纪要模块和历史管理模块。各模块之间并不是完全孤立的，例如智能纪要模块既可以上传新音频，也可以直接复用录音转文字模块历史中的音频与文本结果；声纹模块既可做单次对比，也可为智能纪要提供说话人匹配支撑。这种设计提高了数据复用率，也体现了项目的系统性。

建议在本章配一张系统总体架构图，图中至少包含以下元素：Vue 前端、Spring Boot 后端、MySQL、MinIO、FunASR、XTTS、CAM++，并用箭头标明“HTTP 调用”“WebSocket 代理”“历史写库”“音频入桶”等关系。

## 第三章 详细设计

### 3.1 界面设计

系统前端首页顶部提供统一导航，左侧边栏按业务流程排列“录音转文字、文字转语音、智能纪要、实时语音、声纹对比”五个核心入口，界面整体采用浅色卡片式布局，适合教学展示。各页面都尽量保持相同的交互风格，例如上传区域、结果区域、历史抽屉和状态提示位置基本一致，这样可以降低学习成本。以“声纹对比”页面为例，界面中明确区分音频 A、音频 B、相似度展示区、历史记录入口和发言人档案管理入口，功能边界清晰，便于老师现场理解系统用途。

### 3.2 后端与数据设计

后端采用 Spring Boot 3.4.1 与 MyBatis-Plus 实现，统一暴露 REST 接口和实时 WebSocket 代理。用户认证部分提供注册、登录和用户信息接口，登录后使用 JWT 进行身份校验；受保护接口包括历史记录、MinIO 音频访问、文字转语音、声纹对比、发言人档案和会议纪要等模块。

数据库中与本项目直接相关的核心表包括：用户表、录音转写历史表、文字转语音历史表、声纹对比历史表、发言人档案表、会议纪要表和会议片段表。数据库主要保存三类信息：一类是业务主记录，例如一次识别、一次合成、一次声纹比对；二类是结构化结果，例如转写文本、关键词、待办项、相似度得分；三类是文件索引信息，例如 MinIO 中的 bucket、object、文件名、文件大小和内容类型。这样做的好处是数据库负责“查得到”，MinIO 负责“存得下”，两者职责分离。

### 3.3 关键技术与算法设计

1. 录音转文字模块  
该模块由前端上传音频，后端接收后先创建历史记录，再把原始音频存入 MinIO，随后调用 Python ASR 服务。Python 端使用 FunASR 的 `paraformer-zh` 模型，并结合 `fsmn-vad` 做端点检测、`ct-punc` 做标点恢复。识别完成后，后端从返回结果中提取文本，连同原始响应一起保存，既方便界面展示，也方便后续调试和答辩说明。

2. 实时语音识别模块  
前端基于浏览器录音能力采集麦克风 PCM 数据，按固定分片持续发送到 Spring Boot 的 WebSocket 接口；Java 后端再把数据转发到 FunASR 的实时 WebSocket 服务。该方案的关键价值在于：前端只面对本项目自己的后端接口，不需要直接处理模型服务地址、鉴权和历史落库问题。识别结束后，系统会把实时音频与识别文本一起保存，形成完整的可追溯记录。

3. 文字转语音模块  
该模块要求用户上传一段参考音频并输入待合成文本，后端把参考音频和文本统一转发到 Python TTS 服务。Python 端使用 XTTS v2 多语言语音合成模型，当前实现支持 `neutral`、`happy`、`sad`、`angry` 四种情感，以及 `zh-cn`、`en`、`es`、`fr`、`de` 五种语言。后端在得到合成结果后，会分别把参考音频和结果音频存入 MinIO，并记录情感、语言、输出格式等元数据。

4. 声纹对比模块  
该模块采用 CAM++ 说话人识别模型。两段上传音频会先在 Python 服务中被统一转成 16k、单声道 WAV，再进行相似度计算。服务端返回 `score`、`threshold`、`is_same_person` 和文字判断结果，后端再把两段原始音频、比对结果和原始响应一起保存。当前实现中阈值采用 0.25，适合在项目演示中给出较直观的“同一人/不同人”结论。

5. 智能纪要模块  
该模块是本项目最能体现综合开发能力的部分。其处理流程为：首先获得完整转写文本；然后按句切分文本，提取关键词和待办事项；如果用户提前选择了发言人档案，系统还会调用 `ffprobe` 获取音频时长，使用 `ffmpeg` 的静音检测能力进行片段切分，再对每个片段重新转写并调用声纹服务进行说话人匹配，最终形成“发言片段”和“发言块”两层结构。纪要生成后支持人工纠错、重新保存、导出 TXT/Markdown/DOCX，这一点比单纯展示摘要结果更符合真实办公场景。

需要特别说明的是，本项目中的“智能纪要”并不是简单调用外部大模型直接生成，而是基于现有转写结果做摘要、关键词和待办抽取，并结合声纹模块进行发言人组织。这种方案更符合当前项目实际实现，也更适合在答辩中解释系统可控性与工程实现过程。

### 4.3 测试分析

从当前测试结果看，项目的主要业务链路已经基本打通，尤其是“上传音频 -> 后端转发 -> 模型服务处理 -> 数据库存档 -> MinIO 存储 -> 前端历史展示”这一完整闭环已经能够稳定体现，适合作为比赛作品展示。系统的优点主要体现在三个方面：一是模块完整，具备前后端与多服务协同特征；二是数据可追溯，便于老师查看历史和复现实验；三是具备一定扩展性，后续可继续替换更强模型而不需要推翻整体架构。

同时，测试中也暴露出一个值得如实说明的问题：在较长音频场景下，离线识别链路仍存在超时风险，说明当前版本更适合中短音频或课堂演示环境。后续可考虑通过异步任务队列、长音频分段处理、模型服务性能调优和 GPU 加速等方式继续优化。这部分内容建议在答辩时主动说明，会显得项目更加真实、成熟。

## 第五章 安装及使用

### 5.1 运行环境

后端建议使用 JDK 17、Maven、MySQL 和 MinIO；Python 侧需要安装 FunASR、ModelScope、TTS、FastAPI/Flask 等依赖；前端需要 Node.js 环境。由于系统由多个服务共同组成，首次部署时需要保证数据库、对象存储、Java 后端和三个 Python 服务全部可用。

### 5.2 启动流程

建议按如下顺序启动：

```bash
# 1. 启动 MinIO
minio server /Users/rongyicheng/minio/data --address :9000 --console-address :9001

# 2. 启动 FunASR 文件识别服务
cd /Users/rongyicheng/Desktop/funasr/FunASR
/Users/rongyicheng/miniconda3/envs/openwebui/bin/python asr_server.py

# 3. 启动 FunASR 实时 WebSocket 服务
cd /Users/rongyicheng/Desktop/funasr/FunASR/runtime/python/websocket
python funasr_wss_server.py --port 10095 --device cpu --ngpu 0 --ncpu 4 --asr_model paraformer-zh --asr_model_online paraformer-zh-streaming --vad_model fsmn-vad --punc_model ct-punc

# 4. 启动 XTTS 服务
cd /Users/rongyicheng/Desktop/layout-tts-0.22.0/layout
/Users/rongyicheng/miniconda3/envs/openwebui/bin/python simple_tts_backend.py

# 5. 启动 CAM++ 声纹服务
cd /Users/rongyicheng/Desktop/speech_campplus_sv_zh-cn_16k-common
/Users/rongyicheng/miniconda3/envs/openwebui/bin/python sc_server.py

# 6. 启动 Spring Boot 后端
cd /Users/rongyicheng/Desktop/minio-backend/springboot-minio
mvn spring-boot:run

# 7. 启动前端
cd /Users/rongyicheng/Desktop/layout-voice-factory
npm run serve
```

其中前端在开发环境下通常访问 `http://localhost:8081`，这是因为 `8080` 端口已被 Spring Boot 后端占用。

### 5.3 典型使用流程

用户进入系统后，先完成注册或登录；随后可根据需求选择不同模块。若使用录音转文字，只需上传音频即可查看识别结果，并可在历史中再次打开原始内容；若使用文字转语音，需要先上传参考音频，再输入文本并选择情感、语言和输出格式；若使用声纹对比，需要上传两段音频后获取相似度与结论；若使用智能纪要，可以上传会议录音或直接从历史转写记录中导入，再查看摘要、关键词、待办和导出文档。

## 第六章 项目总结

“特辣油语音工厂”并不是简单把几个页面拼接起来，而是围绕“语音数据的上传、处理、存储、回看、再利用”构建了一条较完整的软件应用链路。项目的主要成果包括：完成了多模块统一前端交互；实现了基于 Spring Boot 的统一服务编排；打通了语音识别、实时转写、语音合成、声纹比对和智能纪要多个功能模块；建立了 MySQL 与 MinIO 结合的数据留存方案；支持历史回溯、人工纠错和多格式导出，具备较好的展示性和实际应用价值。

从开发过程来看，项目最大的收获在于把单点模型能力转化为可用的软件系统。相比单独演示某个 Python 脚本，本项目更加突出接口组织、数据建模、服务解耦和用户体验设计，这也是软件应用类比赛更看重的部分。与此同时，项目也存在继续提升的空间，例如长音频超时优化、TTS 服务常驻化以减少冷启动、前端静态资源体积优化、智能纪要算法进一步增强、Docker 化部署等。这些内容都可以作为后续迭代方向。

答辩时建议重点强调三点：第一，项目是“多语音能力融合的系统工程”，不是单功能 Demo；第二，项目具备“历史留存和结果可追溯”能力，符合真实业务场景；第三，项目已经完成真实联调和本地运行验证，具备进一步优化和推广的基础。
